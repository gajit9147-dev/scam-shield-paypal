# Day 3: measured general-spam baseline and cautious payment warnings

The UCI SMS Spam Collection is [English general SMS spam](https://archive.ics.uci.edu/dataset/228/sms+spam+collection), not UPI/payment scam data. We train a word/unigram-bigram (with number masking) multinomial Naive Bayes model on Day 2's 4,128 training rows, inspect performance on 516 validation rows with a conservative 0.95 threshold, and evaluate **once** on 516 frozen test rows. Run `python scripts/fetch_uci.py`, `python scripts/prepare_data.py`, `pip install scikit-learn==1.5.2 scipy==1.14.1`, then `python scripts/train_spam.py` to rebuild. The Python tool exports fixed word weights to JSON for the Node server, so live inference needs no Python or third-party API.

The held-out **general-spam** test confusion matrix is TP 62, FP 1, TN 446, FN 7 (spam as positive), precision 98.41%, recall 89.86%, accuracy 98.45%. The majority-ham baseline accuracy is 86.63% with zero spam recall. The fixed conservative threshold is 0.95, with validation TP 48, FP 5, TN 459, FN 4; we did not adjust the threshold on the test set. See [machine-readable metrics](uci-test-metrics.json) for full counts and the ID of one false positive. These numbers are **not** scam detection metrics; there are zero evaluated UPI examples here. Validation and test data are not in the repo. The Day 2 script shuffles with seed 42, but does not actually stratify per label despite its docstring; the realized class counts are in `data/processed/stats.json`. We have not altered the frozen split to improve scores.

At `/api/check`, a small deterministic warning rule flags messages that request an OTP/PIN/password, or combine a pay/transfer demand, credit/account-threat language and a destination. It can miss scams and falsely flag benign quotation or security training text. The trained general-spam score appears only as a separate `generalSpamSignal`; it does not automatically turn spam into `scam` or ham into `safe`. `scam` is a warning about suspicious text patterns, not verified sender intent. Everything else returns `uncertain`, including ordinary payment notices. No `safe` response is produced, because text alone cannot verify a real payment. Confidence in the **scam** label is null: a UCI spam score cannot supply it. No UPI precision, recall, false-positive rate, coverage or loss-prevention claim is defensible yet.

Before expanding the rules or issuing `safe`, collect consented, redacted real India/UPI payment messages, separately labeled under `docs/architecture.md`; group near-identical templates and senders across splits and freeze a UPI test set. On that set, report TP/FP/TN/FN, scam precision and recall, abstention/coverage and false-positive examples. Keep private messages, identifiers and links out of Git. The API does not log or store submitted bodies, though the user should not paste private messages into a public demo. Always verify in the bank or payment app independently.
